# Welcome to your Expo app 👋

This is an [Expo](https://expo.dev) project created with [`create-expo-app`](https://www.npmjs.com/package/create-expo-app).

## Get started

1. Install dependencies

   ```bash
   npm install
   ```

2. Start the app

   ```bash
   npm start
   ```

   `npm start` uses the computer's LAN address so a physical iPhone can connect
   over the same Wi-Fi network. In Expo Go, scan the new QR code after the
   terminal finishes starting. Do not reuse a QR code that contains `127.0.0.1`
   or `localhost`.

   The equivalent explicit command is:

   ```bash
   npm run start:lan
   ```

   The iPhone and computer must be on the same Wi-Fi network, and the
   computer's firewall must allow Node.js through private networks.

   Tunnel mode is also available when the network supports ngrok:

   ```bash
   npm run start:tunnel
   ```

In the output, you'll find options to open the app in a

- [development build](https://docs.expo.dev/develop/development-builds/introduction/)
- [Android emulator](https://docs.expo.dev/workflow/android-studio-emulator/)
- [iOS simulator](https://docs.expo.dev/workflow/ios-simulator/)
- [Expo Go](https://expo.dev/go), a limited sandbox for trying out app development with Expo

You can start developing by editing the files inside the **app** directory. This project uses [file-based routing](https://docs.expo.dev/router/introduction).

## Email verification for new accounts

Customer and vendor registrations require users to enter a one-time email code.
The backend asks Supabase Auth to generate and verify the OTP, then sends it
through Gmail SMTP using credentials in `server/.env`; Supabase's email sender
and email template are not used. In Supabase, keep **Confirm email** enabled
under **Authentication → Sign In / Providers → Email**; do not enable automatic
email confirmation. After verifying a vendor account, the user must upload
their National ID or passport, hotel/property document, and government business
registration document before an administrator can approve the account.

To configure Gmail, enable 2-Step Verification on the Gmail account, create an
App Password, then copy `server/.env.example` to `server/.env` and set
`SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=465`, `SMTP_SECURE=true`, `SMTP_USER`
to the full Gmail address, `SMTP_PASS` to the App Password, and
`SMTP_FROM_EMAIL`/`SMTP_FROM_NAME` to the sender identity. Port 587 uses
`SMTP_SECURE=false`. Keep these settings only in `server/.env`; never put them
in the Expo app's `.env` or client code. Restart the backend after changing
settings. The backend limits repeated OTP emails to one per minute per email.
The OTP input length is taken from the code generated by Supabase Auth, and the
expiry countdown uses `AUTH_OTP_EXPIRES_IN_SECONDS`. Keep that setting in sync
with **Authentication → Sign In / Providers → Email → Email OTP expiration**
in Supabase; the default is 3600 seconds. The same SMTP settings send vendor
approval and rejection emails. If a decision is saved but delivery fails, the
admin vendor screen reports the failure and offers a **Resend decision email**
action.

## Booking notifications and payments

Apply every Supabase migration in `supabase/migrations` in order. This includes
`0006_monime_checkout_sessions.sql`, which stores Monime's checkout session ID
for server-side payment verification, and
`0007_vendor_hotel_management.sql`, which lets active, approved vendors publish
new listings immediately. The database continues to enforce vendor approval
and prevents vendor edits from changing ownership, approval status, rating, or
commission. Apply `0008_account_and_record_deletion.sql` as well: deleting a
user profile also removes its Supabase Auth account; deleting an account removes
its properties and non-financial dependent records. Bookings, payments, and
payouts are retained as history with deleted user/property references set to
null. The migration also removes Auth accounts left without a matching
`public.users` profile. Apply `0009_vendor_documents_bucket.sql` to create or
restore the private `vendor-documents` Storage bucket used for vendor
verification documents (10 MB bucket limit; the document upload flow is capped
at 5 MB and accepts PDF, JPG, and PNG). Apply
`0010_vendor_terms_schema_repair.sql` if the live database reports that
`users.vendor_terms_accepted_at` or `users.vendor_terms_version` is missing;
it idempotently adds those columns and restores the vendor signup trigger.
Apply `0011_hotel_rejection_reason_repair.sql` if the live database reports
that `hotels.rejection_reason` is missing; it safely adds the nullable review
note column used by vendor and admin hotel screens. Apply
`0017_repair_payment_session_schema.sql` if payment setup reports that
`payments.provider_session_id` is missing; it restores the column and index
and asks PostgREST to reload its schema cache.
Apply `0018_system_room_availability.sql` to enable date-specific room
availability and 15-minute checkout holds. Availability is calculated from
paid bookings and active pending holds; failed, cancelled, and expired pending
bookings no longer reserve inventory. The booking form relies on the migration's
`get_room_availability` RPC for room counts, while `create_booking` rechecks
inventory atomically before creating a hold. Pending holds expire 15 minutes
after booking creation, and the payment service refuses to start checkout after
that deadline.
Apply `0019_guest_booking_cancellation.sql` to enable the authenticated guest
cancellation RPC and the saved-hotels RPC used to load a user's complete saved
hotel cards, including listings that are no longer publicly visible. Paid
bookings are not cancelled in-app because refunds must be handled through
support.
Apply `0020_repair_booking_updated_at.sql` if cancellation reports that
`bookings.updated_at` is missing; it safely restores the column required by
booking status updates.
Apply `0021_repair_favorites_created_at.sql` if Saved hotels reports that
`favorites.created_at` is missing; it restores the timestamp used to order
saved hotels.
Apply `0022_vendor_document_requirements.sql` through
`0029_wallet_role_detection_fix.sql` in numeric order for three-document
vendor verification, booking commission and payout recording, wallet
withdrawals, and account controls. Apply
`0030_remove_vendor_plans_keep_commission.sql` to remove legacy vendor plans,
plan payments, and hotel-count limits, then apply
`0031_monime_test_payment_verification.sql` for Monime test-mode paid booking
and simulated earnings, followed by
`0032_monime_test_payment_simulation.sql` to simulate `mon_test_` booking
payments as Le 1 pending TEST transactions without calling Monime. The TEST PIN
is `1234`; live tokens continue to use Monime checkout. Apply
`0033_booking_voucher_pgcrypto_search_path.sql` to ensure payment confirmation
can access pgcrypto when issuing booking vouchers. Apply
`0034_admin_test_fund_release.sql` to enable the admin release action for paid
Le 1 TEST bookings; it updates the vendor's eligible wallet balance without
transferring real funds. Apply `0035_test_payment_method_details.sql` to store
the selected TEST wallet label and phone number on its payment record. All
active vendors then use the same
administrator-configured booking commission. Vendor documents remain in
a private Storage bucket; administrators and the document owner use
short-lived signed links to view them. Earnings are recorded for dashboard
display only; the project does not automatically transfer payouts.

To delete a user, use **Authentication → Users** in the Supabase dashboard, or
delete the matching row from `public.users` after applying migration 0008. If
signup still says an email exists before that migration is applied, remove the
email's leftover account from **Authentication → Users** or sign in/reset its
password. Supabase Storage files are separate objects and are not removed by
database foreign-key cascades.

Configure the backend:

1. Install backend dependencies with `npm install --prefix server`. If
   `server/.env` does not exist, copy `server/.env.example` to `server/.env`;
   otherwise edit the existing file. Set the SMTP values described above and
   add the Monime settings below. Do not commit `server/.env`.
2. For **Live mode**, enter your Monime Live `MONIME_ACCESS_TOKEN` and
   `MONIME_SPACE_ID` in `server/.env`. Live access tokens start with `mon_`
   (not `mon_test_`) and Space IDs start with `spc-`. Add the signing secret
   for your Live webhook as `MONIME_WEBHOOK_SECRET`. Keep
   `MONIME_MODE=LIVE`, `MONIME_CURRENCY=SLE`, and
   `MONIME_API_VERSION=caph.2025-08-23`. For TEST simulation, use a
   `mon_test_` token and set `MONIME_MODE=TEST`; the app simulates a Le 1
   payment using PIN `1234` without calling Monime or moving money. The
   simulated vendor earnings remain pending until an administrator releases
   them. Live credentials continue to use Monime checkout. The backend rejects
   a mode/token mismatch and `/api/health` reports the mode loaded by the
   running server. Do not mix test and live credentials.
3. Set `SUPABASE_URL` and `SUPABASE_SECRET_KEY` in that same backend-only file
   for server-side Auth OTP generation and payment verification. The secret key
   must be enabled for the same Supabase project; existing installations may
   keep using    `SUPABASE_SERVICE_ROLE_KEY` for a legacy service-role JWT. Set
   `PAYMENT_CALLBACK_URL` to
   `https://<your-public-backend-host>/api/payments/return`. Monime requires a
   public HTTPS return URL; the backend redirects that URL into the app's
   `hotelmanagement://payment/callback` route.
4. In the Monime **Live** dashboard, register
   `https://<your-public-backend-host>/api/payments/monime-webhook` as a
   webhook URL, subscribe to `checkout_session.completed`,
   `checkout_session.cancelled`, and `checkout_session.expired`, and use that
   webhook's signing secret for `MONIME_WEBHOOK_SECRET`. The backend verifies
   the signature and re-fetches the session from Monime before changing the
   payment status. A local `localhost` URL is not reachable by Monime.
5. Start the backend with `npm run server`. Set
   `EXPO_PUBLIC_BACKEND_URL` in the project-root `.env` to the backend's
   reachable LAN or deployed HTTPS URL so the app can call it.

Live mode processes real payments. Confirm the Live Space, currency,
settlement details, webhook secret, and production HTTPS backend before
accepting customer payments. The app redirects customers to Monime Checkout
and verifies the checkout session against Monime's API before marking a
booking paid. Never put `MONIME_ACCESS_TOKEN`, `SUPABASE_SECRET_KEY`, or
`SUPABASE_SERVICE_ROLE_KEY` in the project-root `.env`, an `EXPO_PUBLIC_*` variable,
`server/.env.example`, or app code.
